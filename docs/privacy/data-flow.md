> **Amendment (2026-07-01, plan 4B):** This document replaces the previous
> "no account / no server database / no saved history" boundary under that
> document's own amendment clause ("must … explicitly replace it with an
> approved contract"). The privacy page, the Play Data Safety mapping
> (`docs/ops/play-twa-runbook.md`), and `docs/legal/counsel-brief.md` were
> updated in the same PR — the lockstep rule.

## Purpose

Revora now has two data postures:

- **Guest:** identical to the original privacy-minimal contract — raw food
  and A1C live only inside the request; nothing is persisted server-side.
- **Account (explicit Art. 9 consent):** meal checks and the A1C are
  persisted to power history, insights, progress, and the nudge — with the
  special-category fields encrypted at rest and excluded from every log,
  error report, and analytics event.

## Raw-input lifetime (per check)

1. The browser sends `food` and `a1c` to `POST /api/check` (engine contract
   unchanged), plus two optional metadata headers: `x-revora-client-id`,
   `x-revora-input-method` (`text`|`voice`).
2. The route delegates to `checkFood()` → single OpenAI Responses call with
   `store: false` → validated response.
3. **Guest:** nothing else happens; raw inputs drop with the request.
4. **Signed-in, `result` kind only:** the route persists one `checks` row:
   `food` as AES-256-GCM ciphertext (`lib/server/crypto.ts`, key
   `HEALTH_DATA_KEY`), plaintext coarse fields (`risk`, `a1c_band`,
   `input_method`, timestamps). Persistence is fail-soft: a DB outage never
   affects the check response.

## Stored-data allowlist (the approved contract)

| Store | Field | Protection |
|---|---|---|
| `users` | email | access-controlled; used for magic links only |
| `profiles` | exact A1C | **ciphertext only** (`a1c_ciphertext`) |
| `profiles` | A1C band, timezone, nudge prefs, consent timestamp | plaintext (coarse) |
| `checks` | meal text | **ciphertext only** (`food_ciphertext`) |
| `checks` | risk class, band, input method, client id, timestamps, action-done | plaintext (coarse) |
| `push_subscriptions` | endpoint + keys; confirmed-send day; bounded local-day attempt count, retry time, and opaque lease | opt-in only; no notification content or health data; attempt state clears on success/preference change or after its local day; row deleted on opt-out/account deletion |
| `subscriptions` | provider ref, product, status, period end | no payment instruments — Play/Stripe hold those |
| `bai_weekly` | behavioral scores | derived, qualitative-banded |
| `pantry_orders` | buyer email (plaintext), Stripe refs, order status | email is the Stripe checkout address, used to send the intake link + report; no payment instruments |
| `deletion_log` | sha256(user id), timestamps | retains no identity |
| `gdm_profiles` | appointment date | **ciphertext only** (`appointment_ciphertext`) |
| `gdm_profiles` | row existence (= told she has gestational diabetes), consent timestamp | plaintext (coarse); written only after explicit consent |
| `gdm_items` | parked questions, plan entries, meals, a photo of her sheet | **ciphertext only** (`body_ciphertext`, JSON) |
| `gdm_items` | kind, timestamps | plaintext (coarse) |

**Never stored anywhere:** plaintext food, plaintext exact A1C, prompt text,
full model output, audio (voice is transcribed on-device/in-browser; servers
receive final text only), payment card data.

Nudge recovery metadata is operational rather than behavioral content. It
contains a local date, a count capped at three, timestamps, and a random lease
token. It never contains notification copy, device activity, meal text, A1C,
email, or a provider response. A successful send clears it; preference changes
clear it; an opted-in stale prior-day attempt is cleared by the next hourly
worker; subscription/account deletion removes the entire row.

## Encryption & key handling

AES-256-GCM via `node:crypto`; fresh IV per value; payload
`base64(iv‖tag‖ciphertext)`; key = `HEALTH_DATA_KEY` (32-byte base64 env,
generated by the operator, stored in Vercel env + secret manager). Rows that
fail decryption degrade to a placeholder — never an error path that dumps
ciphertext into logs. KMS is the upgrade path (docs/adr/stack.md).

## Access control

- `GET /api/history` decrypts food **only for the authenticated owner**
  (session → `user_id` scoping in every query; cross-user reads are
  impossible by construction and tested — `history-routes.test.ts`).
- `GET /api/profile` never returns the exact A1C, only the band.
- All account routes 401 without a database session.

## Deletion

`POST /api/account/delete` removes the user row; every user-linked table
cascades (`ON DELETE CASCADE`, tested for zero residual rows). A hashed-id
audit row is written to `deletion_log`. Public deletion URL:
`/account/delete` (declared in Play's Data-deletion field).

## Telemetry / Sentry / analytics allowlist

Unchanged in spirit, extended in scope. Allowed: event name, environment,
response kind, risk class, latency bucket, coarse reason code, input method.
**Excluded, enforced by tests:** raw food, raw/exact A1C, ciphertexts, prompt
text, model output, email, user identifiers. The Sentry `beforeSend` scrubber
deletes `request`/`user`/`extra`/`contexts`/`message`/breadcrumbs and redacts
exception values — which structurally covers the new fields (email,
`food_ciphertext`, decrypted food, exact A1C); `sentry-scrub.test.ts` +
`privacy-stateful.test.ts` assert it.

## Provider storage posture

Every Responses call still goes through `lib/revora/openai-client.ts` with
`store: false`. No overclaim of zero retention: provider-side
abuse-monitoring logs can exist. OpenAI DPA execution is a Track C human
action.

## Health probe

`GET /api/health` may expose only minimal non-secret JSON (`ok`,
`environment`, `launch`, probe booleans like `db`). Never secrets, raw
inputs, prompt text, or model output.
